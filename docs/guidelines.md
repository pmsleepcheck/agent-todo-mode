# 通用工程准则

> 🚦 **开工前请先读**：[`dev_workflow.md`](dev_workflow.md) —— 任何跨 2 个及以上文件 _或_ 对运行时 / 构建 / 外部行为有可观察变化的任务，必须先在 [`docs/todos/`](todos/) 建立 TODO 文档，功能完成时在文档底部标注并实际执行自刷新。本文档约束「怎么写」，dev_workflow 约束「怎么走流程」。

## 重要说明

本准则是一个动态文档，会随项目发展而演进。实践中的任何变更都必须更新到本准则中，特别是架构部分必须与实际项目结构保持一致。

本文档语言无关：具体用什么语言、框架、状态管理方案与目录结构，以各项目根目录 [`AGENTS.md`](../AGENTS.md) 的「项目概览 / 架构」章节为准；两者冲突时以实际代码为准。

## 1. 架构设计准则

### 1.1 解耦原则
- 严格遵循 SOLID 原则
- 使用依赖注入管理组件依赖
- 业务逻辑与 UI 分离，采用统一的表现层模式（MVVM / BLoC / Redux / 分层 + 状态容器等，**由项目 AGENTS.md 定义**）
- 使用接口 / 抽象定义模块间通信契约

### 1.2 模块化原则
- 按功能划分模块
- 遵循单一职责原则
- 模块间通过清晰的接口通信
- 共享组件放置在公共目录（如 `common/` / `shared/`）下

### 1.3 代码组织

分层建议（具体目录名由项目 AGENTS.md 定义，且必须与实际代码一致）：

| 层 | 职责 | 典型内容 |
| :--- | :--- | :--- |
| 核心层 | 平台服务与基础设施 | 依赖注入、主题、网络、日志、工具 |
| 数据层 | 对外部数据的访问与转换 | 数据模型、仓库实现、服务客户端 |
| 领域层 | 业务规则（可选，按项目复杂度取舍） | 实体、仓库接口、用例 |
| 表现层 | 用户交互 | 页面 / 视图模型 / 组件 |
| 通用层 | 跨模块复用 | 常量、扩展方法、通用组件 |

### 1.4 文案 / 字符串管理
- 所有**用户可见文案**必须集中定义在项目的文案常量文件中
- 禁止在代码中使用硬编码的用户可见字符串
- 文案常量按功能模块分组管理
- 为后续国际化做好准备
- 命名应清晰表达其用途
- **豁免**（不进文案常量文件）：抛出的异常消息、诊断日志、枚举标签——它们经错误处理层翻译后才面向用户（见 §3.3）

示例（语言无关示意）：

```
文案常量文件
  appName = 'MyApp'
  loading = '加载中...'
  search  = '搜索'
```

## 2. UI/UX 设计准则

### 2.1 界面设计
- 遵循目标平台设计规范（Material Design 3 / Apple HIG / 项目自有设计系统）
- 使用一致的颜色主题和字体
- 保持视觉层次感和空间布局的平衡
- 注重细节，保持像素级别的对齐
- **无障碍**：可点击元素最小触达 48×48；图标按钮提供 tooltip 或语义标签；正文对比度 ≥ 4.5:1；尊重系统「减弱动效」设置

### 2.2 动画效果
- 使用框架内置动画系统
- 微交互持续时间保持在 200–300ms 之间
- 使用缓动曲线动画（推荐 easeInOut 类曲线）
- 实现平滑的页面转场效果
- 添加有意义的微交互动画

### 2.3 性能优化
- 使用 `const` / 不可变构造，避免在渲染 / 构建路径上做复杂计算
- 长列表用惰性构建（builder 模式）
- 图片资源进行适当压缩和缓存
- **订阅范围最小化**：高频事件（如播放位置、滚动进度）不要走全员广播的通知器，改用独立的轻量监听
- **禁止在滚动 / 构建路径上引入 per-item 的数据库或文件系统查询**——需要整页附加信息时批量查一次
- **启动路径**：不在构造期做网络与重 IO；非首帧必需的初始化推迟到首帧之后；权限在首次真正使用时才请求；启动期可能挂起的等待必须有超时保护

## 3. 代码质量准则

### 3.1 代码风格
- 遵循目标语言的官方风格指南
- 使用格式化工具统一格式
- 类型安全，避免 `dynamic` / `any` 滥用
- 添加必要的注释——**只写「为什么」，不写「做了什么」，不写变更史**

### 3.2 测试规范
- 单元测试覆盖率目标由项目设定（默认建议 > 80%）
- 编写组件 / UI 测试验证交互行为
- 集成测试覆盖关键业务流程
- 使用 mock 进行依赖隔离
- **测试不得依赖真实网络**——用拦截器 / 假客户端在边界处短路
- **断言共享常量本身，不复制它的值**：把常量字面量抄进测试，测试就成了常量的影子，每次调参都要跟着改
- **尽量经真实调用点断言**（挂载真实页面 / 真实调用方，而非孤立组件）——同时覆盖「组件坏了」和「调用方传错」两类缺陷

### 3.3 错误处理与用户提示
列表页 / 任务型界面的错误提示必须传达**正确的恢复动作**，不是「出错了 + 重试」四个字：

1. **数据层**：统一的错误翻译层集中生成用户文案（连接失败 → 检查网络/代理；鉴权失败 → 去登录；其余 → 可重试的通用提示）。禁止把异常 `toString()` 直接上屏。
2. **视图模型层**：区分「未登录」与「可重试错误」两种状态位；每次加载前重置，避免旧错误残留。
3. **组件层**：未登录且提供了登录入口时，按钮显示「去登录」而非「重试」（重试一个未登录请求毫无意义）。
4. **加载 / 错误态编排**：loading 与 error **只在数据为空时**才替换内容——分页中失败不得把已有列表换成错误页、不得丢滚动位置；空态必须有可见提示。

诊断信息留在日志里，用户文案走文案常量（§1.4）。

## 4. 版本控制准则

### 4.1 Git 规范
- 使用 Feature Branch 工作流
- commit 信息遵循 Angular 规范
- 定期进行代码审查
- 保持 main 分支稳定可用
- **纯格式化改动与功能改动分开提交**——混在一起的 diff 无法审查

### 4.2 发布规范
- 遵循语义化版本控制
- 每次发布都要有清晰的更新日志
- 重要版本发布前进行完整测试（用生产配置 / profile 模式验证性能，debug 数据不作数）
- 保留每个版本的文档更新

## 5. 项目管理准则

### 5.1 文档管理
- 及时更新 API 文档
- 维护清晰的 README
- 记录重要的设计决策
- 编写用户指南和开发指南
- **易碎不变量就地文档化**：顺序敏感的写入、并发去重、平台分支等逻辑，改它之前必须在文档 / 注释里写明「为什么不能改回去」，防止后续会话以「简化」为名回退
- 架构文档与代码冲突时**以代码为准**，并在下次文档自刷新时修正文档

### 5.2 问题追踪
- 使用 Issue 跟踪 bug 和新功能
- 为每个 Issue 添加适当的标签
- 保持任务的可追踪性
- 定期回顾和更新任务状态
